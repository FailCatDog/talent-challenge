# 项目全生命周期与里程碑流转修改方案

## 1. 目标
基于当前项目已有代码结构，整理一套“改动成本较低、逻辑闭环完整”的修改方案，使项目状态、揭榜状态、里程碑状态三者保持一致，避免出现“项目已开始但里程碑未启动”或“里程碑已全部结束但项目未收口”的问题。

## 2. 当前实现概况
现有代码已经具备以下基础能力：

- 项目状态：`draft`、`pending_review`、`rejected`、`published`、`in_progress`、`completed`、`closed`
- 项目创建后会初始化必选里程碑
- 项目中标后会进入 `in_progress`
- 当前里程碑审批通过后，会尝试启动下一里程碑

说明当前系统已经有“项目驱动里程碑执行”的基础，只是生命周期收口和部分边界规则还不完整。

## 3. 推荐的完整生命周期
建议按以下流程收敛：

1. 企业创建项目，项目状态为 `draft`
2. 企业补全项目信息和里程碑计划
3. 企业提交审核，项目状态变为 `pending_review`
4. 审核通过后，项目状态变为 `published`
5. 团队在 `published` 阶段揭榜
6. 企业确认中标后：
   - 中标揭榜状态变为 `confirmed`
   - 项目状态变为 `in_progress`
   - 初始化并启动首个可执行里程碑
   - 其他活跃揭榜申请变为 `rejected`
7. 项目执行中，里程碑按顺序推进
8. 最后一个必选里程碑审批通过后，项目状态自动变为 `completed`
9. 项目完成后的收尾或归档动作，再进入 `closed`

## 4. 建议修改点

### 4.1 项目创建阶段
建议保留当前“创建项目时初始化必选里程碑”的方式，不必推翻现有实现。原因是：

- 当前前后端与审核逻辑已依赖里程碑存在
- 提交审核前也会校验里程碑描述和计划时间
- 继续沿用现方案改动最小

建议补充约束：

- `draft` 阶段允许维护项目和里程碑
- 非 `draft/rejected` 状态下禁止随意修改里程碑基础计划

### 4.2 揭榜阶段
建议将揭榜申请限制在 `published` 状态，原则上不要允许 `in_progress` 阶段继续新增揭榜。这样可以避免项目已经执行但仍在持续招募的状态混乱。

如果短期不想改动接口行为，也建议至少在文档和后续需求中明确：`in_progress` 下新增揭榜是否为允许业务。

### 4.3 中标确认与项目启动
保留当前基于 `BidConfirmedEvent` 的异步同步模式，建议继续由消费者统一完成：

- 绑定中标团队
- 项目改为 `in_progress`
- 初始化必选里程碑
- 启动首个可执行里程碑
- 拒绝其他揭榜申请

这一段应该继续作为“项目启动”的统一入口，不建议散落到多个控制器中实现。

### 4.4 里程碑推进规则
建议统一为以下主路径：

- `planned -> in_progress`
- `in_progress -> delivered`
- `delivered -> completed / rejected`

结合当前代码实际使用情况，`under_review` 状态虽然在枚举和状态机中存在，但主业务流程并未真正依赖它。为了项目当前版本尽快上线，本阶段不删除该状态定义，先保留但不在主流程中使用，里程碑执行链路直接采用“提交成果后进入审批，审批后直接完成/驳回”的模式。

也就是说，当前推荐方案是：

- 状态定义层面保留 `under_review`
- 生命周期主流程中直接跳过 `under_review`
- 后续如果新增更细的评审环节，再重新启用该状态

这样做的好处是：

- 改动成本低，符合当前上线优先原则
- 与现有审批实现更一致
- 为后续扩展评审中场景保留空间

### 4.5 下一里程碑自动启动
建议保留“当前节点通过后自动启动下一节点”的机制，但补齐以下规则：

- 只启动下一个有效节点
- 若下一个节点已跳过，则继续向后找
- 若下一个节点已不是 `planned`，则不重复启动
- 启动时统一补齐开始时间、计划时间、进度等必要字段

当前已实现基础自动启动，后续可逐步增强“跳过节点/可选节点”的查找规则。

### 4.6 项目完成与关闭
建议新增一条收口规则：

- 当最后一个必选里程碑审批通过后，项目状态自动更新为 `completed`

后续若存在财务结算、归档、人工确认收尾等操作，再从 `completed` 进入 `closed`。

这样可以把：

- `completed` 定义为“业务执行完成”
- `closed` 定义为“流程彻底收口”

## 5. 实施优先级建议

### 第一阶段：低成本闭环
优先完成以下内容：

1. 中标后启动首个里程碑
2. 审批通过后自动启动下一里程碑
3. 最后一个里程碑完成后自动把项目改为 `completed`

这一阶段可以先形成“项目启动 -> 里程碑推进 -> 项目完成”的基本闭环。

### 第二阶段：规则收敛
再逐步处理：

1. 限制揭榜只发生在 `published`
2. 统一审批流和状态机
3. 明确 `skipped`、可选里程碑的推进规则
4. 明确 `completed -> closed` 的操作入口

## 6. 推荐原则
本项目后续修改建议遵循以下原则：

- 项目状态只表达项目总体阶段
- 里程碑状态只表达执行进度
- 项目进入 `in_progress` 时必须存在当前执行中的里程碑
- 全部必选里程碑结束后，项目必须有明确收口动作
- 生命周期主入口尽量集中在领域服务和事件消费者，不在控制器层堆叠业务逻辑

## 7. 总结
从当前代码基础看，最适合的方案不是推翻重做，而是在现有实现上补齐闭环：

- 保留“创建项目即初始化里程碑”
- 保留“中标事件驱动项目启动”
- 保留“审批通过自动推进下一节点”
- 增加“首节点自动启动”和“最后节点完成后项目自动完成”

这样实现成本低、兼容现有结构，也最容易在当前项目中稳定落地。
