# 项目里程碑状态流转调研与修改方案

## 1. 背景说明
当前项目存在多个里程碑节点。业务期望是：

1. 企业审批通过当前节点 A 后，A 自动变为已结束。
2. A 的下一个节点 B 自动从未开始变为开始中。
3. 同步更新节点开始时间等相关字段。

本次仅做代码调研，不改动业务代码。

## 2. 现状流程
当前审批入口位于 `MilestoneHttpController.approveMilestone`，调用链如下：

1. 前端调用 `/api/v1/milestone/approve`
2. 进入 `MilestoneService.approveMilestone`
3. 若审批通过：
   - 当前节点状态更新为 `completed`
   - 审批状态更新为 `approved`
   - 进度更新为 `100`
   - `actualEndTime` 更新为当前时间
4. 然后继续调用 `startNextMilestone(projectId, sequenceOrder)`，尝试启动下一个节点

关键代码位置：

- `TalentChallenge-trigger/src/main/java/cn/hgy/trigger/http/MilestoneHttpController.java`
- `TalentChallenge-domain/src/main/java/cn/hgy/domain/project/service/MilestoneService.java`

## 3. 调研结果
结论不是“完全没有自动流转逻辑”，而是“已有部分逻辑，但不完整，且存在关键断点”。

### 3.1 已存在的逻辑
- 当前节点审批通过后，系统会将其改为 `completed`
- 审批通过后，系统会尝试启动紧邻的下一个里程碑
- 下一个节点如果是 `planned`，会被更新为 `in_progress`
- 同时会写入 `actualStartTime`

### 3.2 主要问题
#### 问题一：项目进入进行中后，第一个里程碑没有自动启动
项目中标后，`ProjectStatusSyncConsumer` 只做了：

- 项目状态改为 `in_progress`
- 初始化必选里程碑

但初始化时所有里程碑默认都被创建成 `planned`，没有额外把首个节点自动置为 `in_progress`。这会导致整个里程碑流转链路缺少起点。

关键位置：

- `TalentChallenge-trigger/src/main/java/cn/hgy/trigger/mq/ProjectStatusSyncConsumer.java`
- `TalentChallenge-domain/src/main/java/cn/hgy/domain/project/service/MilestoneTemplateService.java`

#### 问题二：启动下一个节点时，更新字段不完整
当前 `startNextMilestone` 只更新了：

- `status = in_progress`
- `actualStartTime = now`

未同步处理以下信息：

- `plannedStartTime / plannedEndTime`
- `progressPercent`
- `currentOwnerId`
- 其他可能依赖“开始状态”的业务字段

因此从业务视角看，节点虽然被启动了，但“开始后的相关信息”并没有完整落库。

#### 问题三：状态流转规则不完全统一
通用状态更新接口与审批接口使用的流转路径并不完全一致。审批接口中允许从 `delivered` 直接审批通过到 `completed`，但通用状态机定义的是 `delivered -> under_review -> completed`。这会造成状态语义不一致，也增加了排查难度。

#### 问题四：自动推进规则较死
当前只会查找 `sequenceOrder = 当前节点 + 1` 的下一个节点，并要求其状态必须是 `planned`。如果中间有跳过节点、可选节点、顺序空洞，自动推进可能失效。

#### 问题五：缺少测试覆盖
当前未发现针对“审批通过后自动启动下一个里程碑”的专门测试，现有逻辑缺少稳定性验证。

## 4. 修改思路
建议按“最小修复 + 后续优化”两步处理。

### 4.1 最小修复方案
1. 在项目进入 `in_progress` 并初始化里程碑后，自动启动第一个有效里程碑。
2. 保留现有 `approveMilestone -> startNextMilestone` 链路。
3. 在启动下一个节点时，补齐必要字段更新，至少统一处理开始时间、进度、负责人或其他当前业务依赖字段。

### 4.2 稳妥优化方案
1. 统一里程碑状态机，明确每个状态允许的前后流转关系。
2. 将“启动下一节点”的规则抽成独立领域逻辑，避免散落在控制器或接口层。
3. 为以下场景补测试：
   - 首个里程碑自动启动
   - 当前节点审批通过后启动下一节点
   - 下一节点不存在时的处理
   - 下一节点不是 `planned` 时的处理
   - 跳过节点/可选节点下的推进逻辑

## 5. 关键定位点
- 审批入口：`MilestoneHttpController.approveMilestone`
- 审批与自动推进：`MilestoneService.approveMilestone`
- 启动下一节点：`MilestoneService.startNextMilestone`
- 必选里程碑初始化：`MilestoneTemplateService.initializeRequiredMilestones`
- 项目进入进行中后的触发点：`ProjectStatusSyncConsumer.handleBidConfirmed`

## 6. 总结
当前系统已经具备“审批通过后推进下一节点”的基础代码，但缺少完整起点和完整字段更新，因此业务表现上仍像“没有自动流转”。后续实现时，优先补齐“首节点自动启动”和“下一节点启动时的字段补齐”，再统一状态机与测试即可。
