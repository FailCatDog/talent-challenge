# 项目里程碑自动启动实现说明

## 背景
在原系统中，项目审核通过后会进入 `published` 状态，
中标团队确定后项目状态变为 `in_progress`，里程碑会被初始化，但首个里程碑仍保持 `planned` 状态，
导致前端查询 `/api/v1/milestone/project/{projectId}` 时里程碑状态始终是 `planned`，
无法体现项目已正式进入执行阶段。

## 目标
1. **中标确认后** 自动将项目的首个里程碑状态从 `planned` 切换为 `in_progress`，并记录实际开始时间。
2. **里程碑状态变更** 自动记录里程碑的实际开始/结束时间（`actualStartTime`、`actualEndTime`）。
3. 保持现有业务流程不受影响，代码改动仅限于里程碑状态服务和项目状态同步消费者。

## 关键代码改动
### 1. `MilestoneService.updateMilestoneStatus`
- **原实现**：只调用 `milestoneRepository.updateMilestoneStatus(milestoneId, status)`，未记录实际时间。
- **新实现**：
  ```java
  ProjectMilestoneEntity entity = milestoneRepository.queryMilestoneById(milestoneId);
  // 状态流转校验已保留
  entity.setStatus(status);
  // 转为进行中时记录实际开始时间
  if (MilestoneStatusEnum.IN_PROGRESS.getStatusCode().equals(status) && entity.getActualStartTime() == null) {
      entity.setActualStartTime(java.time.LocalDateTime.now());
  }
  // 转为已完成时记录实际结束时间
  if (MilestoneStatusEnum.COMPLETED.getStatusCode().equals(status) && entity.getActualEndTime() == null) {
      entity.setActualEndTime(java.time.LocalDateTime.now());
  }
  milestoneRepository.updateMilestone(entity);
  ```
- **新增日志**：记录 `oldStatus` 与 `newStatus` 以及里程碑 ID。

### 2. `ProjectStatusSyncConsumer.handleBidConfirmed`
- **原实现**：仅更新 `acceptedTeam`、把项目状态改为 `IN_PROGRESS` 并初始化里程碑。
- **新实现**：
  1. 引入 `MilestoneStatusEnum` 与 `ProjectMilestoneEntity`。
  2. 在里程碑初始化后，获取该项目所有里程碑并按 `sequenceOrder` 排序。
  3. 找到第一个 `planned` 里程碑，调用 `milestoneService.updateMilestoneStatus(..., IN_PROGRESS)`，自动把它切换为进行中并记录实际开始时间。
  4. 日志记录自动启动的里程碑信息。
- **额外处理**：保持原有拒绝其他竞标的逻辑不变。

## 业务影响
- **接口 `/api/v1/milestone/project/{projectId}`**：首次查询时返回的里程碑状态将为 `in_progress`（而不是 `planned`），并包含 `actualStartTime`。
- **里程碑状态变更**：当业务将里程碑状态切换为 `completed` 时，`actualEndTime` 会自动写入，便于后续统计与审计。
- **兼容性**：所有已有的里程碑状态流转校验仍然有效，未对外部调用方式产生破坏。
